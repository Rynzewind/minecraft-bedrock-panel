# User release requirements

For every future installer update, build the single-EXE installer, test and Defender-scan it, then publish a checksum-verified latest copy to `G:\My Drive\Minecraft Server Setup\NetherNetSetup.exe`. Use `scripts/release-single-file-setup.ps1`, which implements that workflow and backs up the previous Drive installer before replacement. Keep the existing installed copy and release package aligned when the user requests an application update.

Snapshot defaults belong under `G:\My Drive\Minecraft Server Setup\Backup Snapshots`, with each snapshot in a dated subfolder. Keep raw snapshot staging and archive construction on the local installation volume because Google Drive rejects protected Windows ACLs. Only publish the verified final ZIP bytes to the selected destination; never weaken staging privacy or delete user worlds/backups while packaging a release.

For every future development session, update the project handover with changes, validation, deployment state, open issues and next steps. Publish the latest handover alongside the installer at `G:\My Drive\Minecraft Server Setup\CODEX-HANDOVER.md`; keep the repository handover current too. This Drive destination is explicitly authorized by the user. Keep `NetherNetSetup.exe` there current after application changes, using the tested/scanned/checksummed release workflow above. Do not place installer copies on the Desktop; retain the application shortcut.

Keep the user's GitHub repository `https://github.com/Rynzewind/minecraft-bedrock-panel.git` up to date: commit completed, validated project changes and push the working branch to origin each development session. Record the branch/commit in the handover. Never commit credentials, account stores, private keys, live configuration, worlds, backups or generated installer binaries. Do not force-push or merge into another branch without authorization.
